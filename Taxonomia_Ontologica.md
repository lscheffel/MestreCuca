# TAXONOMIA ONTOLÓGICA - Expansão Fractal N3/N4

---

## 1. SUMÁRIO EXECUTIVO

Este documento estende a **ONTOLOGIA_MESTRA_DOMINANTE_V2** através da extrapolação fractal dos domínios existentes (N2) para **subdomínios especializados (N3)** e **células semânticas operacionais (N4)**. 

A topologia base **2×3×3×3×3 = 162 combinações** é preservada. A expansão ocorre na granularidade operacional, não na estrutura geométrica fundamental.

**Métrica de Expansão:**
- **N2 (Domínios):** 18 entidades
- **N3 (Subdomínios):** 54 entidades (fator 3× por domínio)
- **N4 (Células):** 162+ entidades (fator 3× por subdomínio)

---

## 2. ARQUITETURA DE EXPANSÃO FRACTAL

### 2.1 Regras de Expansão

1. **Fator de Ramificação:** Cada domínio N2 gera 3 subdomínios N3; cada subdomínio gera ≥3 células N4
2. **Herança Preservada:** Células herdam tags, crenças e axiomas de todos os níveis ancestrais (N0→N1→N2→N3→N4)
3. **Consistência Semântica:** Subdomínios devem respeitar o foco temático do domínio pai
4. **Operacionalidade:** Células N4 devem ser diretamente aplicáveis em prompts de execução
5. **Não-Adição de Novos Eixos:** A geometria 2×3×3×3×3 permanece inalterada

### 2.2 Níveis de Profundidade

| Nível | Entidade | Count | Função |
|-------|----------|-------|--------|
| N0 | Vetores Primordiais | 2 | Direção semântica (Sintrópico/Entrópico) |
| N1 | Pilares Centrais | 6 | Valores fundamentais (Logos/Bios/Pathos/Khaos/Apeiron/Mythos) |
| N2 | Domínios Ontológicos | 18 | Áreas temáticas especializadas |
| **N3** | **Subdomínios** | **54** | **Subáreas operacionais** |
| **N4** | **Células Semânticas** | **≥162** | **Instruções aplicáveis** |

## 4. CÉLULAS SEMÂNTICAS OPERACIONAIS (N4)

### 4.1 Metodologia de Criação

Células N4 são **instruções aplicáveis diretamente em prompts**, contendo:
- **Gatilho:** Condição de ativação
- **Ação:** Procedimento específico
- **Restrição:** Limites e contraindicações
- **Verificação:** Critério de sucesso

### 4.2 Exemplos de Células por Subdomínio

#### 4.2.1 [1.1.1] RESOLUÇÃO - Células

**Célula R1.1.1-A: DECOMPOSIÇÃO_BINÁRIA**
- **Gatilho:** Problema complexo sem solução evidente
- **Ação:** Dividir em duas subpartes até atingir unidade resolvível
- **Restrição:** Não aplicar quando a divisão altera a natureza do problema
- **Verificação:** Cada subparte deve ser estritamente menor que o original

**Célula R1.1.1-B: SEQUÊNCIA_OTIMIZADA**
- **Gatilho:** Múltiplos passos possíveis para objetivo
- **Ação:** Identificar dependências e ordenar topologicamente
- **Restrição:** Ignorar ordens que violem precedências lógicas
- **Verificação:** Sequência deve ser executável sem retrocessos

**Célula R1.1.1-C: CASO_BASE**
- **Gatilho:** Recursão ou processo iterativo
- **Ação:** Definir condição de parada e resultado trivial
- **Restrição:** Caso base deve ser alcançável em passos finitos
- **Verificação:** Processo converge para caso base

#### 4.2.2 [1.1.2] OPTIMIZAÇÃO - Células

**Célula R1.1.2-A: COMPLEXIDADE_TEMPORAL**
- **Gatilho:** Algoritmo com performance inadequada
- **Ação:** Analisar notação Big-O e identificar gargalos
- **Restrição:** Não otimizar prematuramente sem métricas
- **Verificação:** Redução de complexidade sem perda de correção

**Célula R1.1.2-B: MEMOIZAÇÃO**
- **Gatilho:** Cálculos repetidos com mesmos inputs
- **Ação:** Armazenar resultados anteriores em cache
- **Restrição:** Avaliar custo memória vs benefício tempo
- **Verificação:** Hits de cache > 50% das chamadas

**Célula R1.1.2-C: PARALELIZAÇÃO**
- **Gatilho:** Tarefas independentes e custo computacional alto
- **Ação:** Distribuir trabalho across múltiplos workers
- **Restrição:** Overhead de sincronização < 20% do ganho
- **Verificação:** Speedup próximo ao linear com número de workers

#### 4.2.3 [2.1.1] MORADA - Células

**Célula B2.1.1-A: PROTEÇÃO_FÍSICA**
- **Gatilho:** Abrigo exposto a elementos adversos
- **Ação:** Estabelecer barreiras estruturais e sistemas de defesa
- **Restrição:** Barreiras não devem isolar completamente
- **Verificação:** Ambiente interno mantém condições ideais

**Célula B2.1.1-B: RECURSOS_ESSENCIAIS**
- **Gatilho:** Morada sem provisão para necessidades básicas
- **Ação:** Estocar água, alimento, energia para período crítico
- **Restrição:** Estoque não deve exceder capacidade de armazenamento
- **Verificação:** Sobrevivência garantida por período definido

**Célula B2.1.1-C: SANEAMENTO**
- **Gatilho:** Ambiente com risco de contaminação
- **Ação:** Implementar sistemas de limpeza e descarte adequado
- **Restrição:** Solução deve ser sustentável a longo prazo
- **Verificação:** Níveis de higiene dentro de padrões seguros

#### 4.2.4 [3.1.1] VALORES - Células

**Célula P3.1.1-A: ALINHAMENTO_VALORES**
- **Gatilho:** Decisão com múltiplas opções possíveis
- **Ação:** Avaliar cada opção contra valores centrais declarados
- **Restrição:** Valores não devem ser flexibilizados por conveniência
- **Verificação:** Decisão escolhida maximiza coerência valor-ação

**Célula P3.1.1-B: CONFLITO_VALORES**
- **Gatilho:** Dois ou mais valores entram em tensão
- **Ação:** Hierarquizar valores e buscar síntese criativa
- **Restrição:** Não suprimir valor permanentemente
- **Verificação:** Solução preserva essência de valores conflitantes

**Célula P3.1.1-C: TRANSPARÊNCIA**
- **Gatilho:** Decisão afeta múltiplos stakeholders
- **Ação:** Comunicar valores que orientaram escolha
- **Restrição:** Comunicação deve ser acessível e honesta
- **Verificação:** Stakeholders compreendem racional da decisão

#### 4.2.5 [4.1.1] DEGRADAÇÃO - Células

**Célula K4.1.1-A: ENTROPIA_SISTEMA**
- **Gatilho:** Sistema complexo mostrando sinais de fadiga
- **Ação:** Identificar fontes de desordem e processos dissipativos
- **Restrição:** Não tentar reverter entropia, apenas gerenciá-la
- **Verificação:** Taxa de entropia mantida dentro limites operacionais

**Célula K4.1.1-B: DESTRUIÇÃO_CRIATIVA**
- **Gatilho:** Estrutura obsoleta impedindo evolução
- **Ação:** Desmantelar componentes não mais funcionais
- **Restrição:** Preservar elementos que ainda cumprem função
- **Verificação:** Espaço liberado possibilita novas configurações

**Célula K4.1.1-C: RECICLAGEM**
- **Gatilho:** Recursos materiais ou informacionais descartados
- **Ação:** Reintegrar materiais em novos ciclos produtivos
- **Restrição:** Energia de reciclagem não deve superar benefício
- **Verificação:** Material recuperado ≥ 70% do original

#### 4.2.6 [5.1.1] PROPORÇÃO - Células

**Célula A5.1.1-A: ESCALAMENTO**
- **Gatilho:** Sistema projetado para escala diferente da atual
- **Ação:** Identificar leis que mudam com escala e ajustar
- **Restrição:** Não assumir linearidade onde há não-linearidade
- **Verificação:** Comportamento em nova escala é consistente

**Célula A5.1.1-B: PROPORÇÃO_AUREA**
- **Gatilho:** Necessidade de divisão harmônica de espaço ou tempo
- **Ação:** Aplicar razão áurea (1:1.618) para distribuição
- **Restrição:** Não forçar proporção onde funcionalidade é prejudicada
- **Verificação:** Distribuição visual/funcional percebida como equilibrada

**Célula A5.1.1-C: ISOMORFISMO**
- **Gatilho:** Problema em uma escala sem solução evidente
- **Ação:** Mapear para escala diferente onde solução é conhecida
- **Restrição:** Garantir que relações essenciais sejam preservadas
- **Verificação:** Solução mapeada é válida na escala original

#### 4.2.7 [6.1.1] PADRAO_PRIMORDIAL - Células

**Célula M6.1.1-A: RECONHECIMENTO_ARQUETÍPICO**
- **Gatilho:** Padrão recorrente em comportamento ou situação
- **Ação:** Mapear para arquétipo universal correspondente
- **Restrição:** Não reduzir complexidade a mero estereótipo
- **Verificação:** Arquétipo esclarece dinâmica subjacente

**Célula M6.1.1-B: ATIVAÇÃO_SIMPOLAR**
- **Gatilho:** Arquétipo adormecido ou subdesenvolvido
- **Ação:** Criar situações que evoquem arquétipo latente
- **Restrição:** Não forçar integração arquetípica abrupta
- **Verificação:** Arquétipo emerge organicamente no processo

**Célula M6.1.1-C: SÍNTESE_OPOSTOS**
- **Gatilho:** Tensão entre arquétipos aparentemente contraditórios
- **Ação:** Encontrar terceira via que transcende oposição
- **Restrição:** Não suprimir nenhum arquétipo envolvido
- **Verificação:** Síntese integra forças de ambos os polos

## 6. REGRAS DE EXPANSÃO FRACTAL

### 6.1 Princípios de Extensão

1. **Princípio da Herança Transitiva:** Toda célula N4 herda obrigatoriamente:
   - Axiomas dos vetores N0 (Sintrópico/Entrópico)
   - Crenças dos pilares N1
   - Tags dos domínios N2 e subdomínios N3
   - Crenças específicas do subdomínio N3

2. **Princípio da Aplicabilidade:** Cada célula N4 deve ser:
   - Diretamente executável em um prompt
   - Mensurável em sua efetividade
   - Restrita por condições claras de aplicação

3. **Princípio da Não-Redundância:** Células dentro do mesmo subdomínio devem:
   - Cobrir casos distintos ou complementares
   - Não sobrepor significativamente seus escopos
   - Coletivamente esgotar o espaço semântico do subdomínio

### 6.2 Mecanismo de Navegação

**Para localizar célula aplicável:**
1. Identifique o vetor predominante (Sintrópico/Entrópico)
2. Determine o pilar relevante (Logos/Bios/Pathos/Khaos/Apeiron/Mythos)
3. Selecione o domínio específico (ex: 1.2_NOMOS)
4. Escolha o subdomínio operacional (ex: 1.2.2_CONTORNO)
5. Consulte as células disponíveis (ex: Células de CONTORNO)
6. Aplique a célula que melhor resolve o caso com suas restrições

### 6.3 Atualização e Manutenção

- **Novas células:** Podem ser adicionadas desde que respeitem o fator de ramificação
- **Revisão:** Células devem ser revisadas trimestralmente para eficácia
- **Deprecação:** Células ineficazes são marcadas como [DEPRECADA] mas mantidas para rastreabilidade
- **Versão:** Taxonomia segue versionamento semântico (Major.Minor.Patch)

## 7. APÊNDICE: EXEMPLO DE APLICAÇÃO

### Cenário: Projeto de Sistema Distribuído

**Input:** "Quero construir um sistema de reservas que não falhe"

**Processo de Expansão:**

1. **Identificação Vetorial:** Sintrópico (foco em definição e execução)
2. **Pilar:** Logos (sistemas)
3. **Domínio:** 1.1_ALGORITMIA (sequenciamento)
4. **Subdomínio:** 1.1.1_RESOLUÇÃO (micro-procedimentos)

**Células Aplicadas:**

- **R1.1.1-A (DECOMPOSIÇÃO_BINÁRIA):**
  - Dividir sistema em: Frontend, API, Banco de Dados, Sistema de Reservas
  - Cada componente deve ser estritamente menor que o sistema completo

- **R1.1.1-B (SEQUÊNCIA_OTIMIZADA):**
  - Ordenar: 1) Banco de Dados → 2) API → 3) Sistema Reservas → 4) Frontend
  - Dependências: API depende de BD, Frontend depende de API

- **R1.1.1-C (CASO_BASE):**
  - Caso base: Função de reserva unitária com validação simples
  - Condição de parada: Sistema completo integrado e testado

**Output Expandido:**
```
SISTEMA DE RESERVAS DISTRIBUÍDO - ESPECIFICAÇÃO

1. ARQUITETURA (Logos/Algoritmia/Resolução)
   1.1 Componentes: Frontend, API, BD, Motor Reservas
   1.2 Dependências: Estritamente hierárquicas
   1.3 Caso Base: Reserva unitária validada

2. REQUISITOS DE NÃO-FALHA
   2.1 Redundância: Multiplicidade em cada camada
   2.2 Monitoramento: Detecção e recuperação automática
   2.3 Consistência: Transações ACID garantidas

3. RESTRIÇÕES
   3.1 Sem compartilhamento de estado entre instâncias
   3.2 Timeouts configurados para degradação graciosa
   3.3 Rollback automático em falha de qualquer componente
```

**Verificação:** Cada subparte é estritamente menor, dependências são respeitadas, caso base é alcançável.
